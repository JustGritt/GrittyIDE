# Task T310-VERDICT-EVENT — Record a permission verdict in a run's event ring

- **Phase:** 4 (orchestration)
- **Status:** todo
- **Depends on:** T310-ANSWER (arm the host permission verdict for an owned run — same files, at review), T310-B

## Objective

A run's console can say what a run asked, but not what it was told. The feed
draws `PERMISSION_REQUESTED`, then `RUN_BLOCKED`, then `RUN_RESUMED` — and
`RUN_RESUMED` follows an allowance and a denial alike. The verdict and its
reason reach the model as a `tool_result` and nothing else: `pending` is
cleared when the answer is accepted, `tracing` records `allowed` but no reason,
and the ring holds no trace. A reader cannot tell a denied call from an allowed
one, which leaves T310's own acceptance criterion half true — "the console
shows what was asked **and why it was denied**" (`docs/tasks/completed/T310-claude-code-adapter.md`).

This task records every permission ending in the run's ring, as an event, so
the console (and later the durable run summary ADR-021 plans) can show it.

## Explicit non-goals

- No change to *what* the child is told. The denial table stays exactly as
  T310-ANSWER left it; this task only records it.
- No `CoreEvent` variant. The record rides `AgentRunEventAppended` like every
  other run event, so `event/mod.rs` and `session/tap.rs` do not change.
- No persistence. Rings are in memory; ADR-021's terminal summary picks up the
  new kind when that task lands.
- No verdict for a **decision** (`NEEDS_DECISION`): answering one has no
  command yet — that is T300-ANSWER (answer a decision on a run Gritty owns).
- No actor identity beyond "the user" versus "a policy". `tracing` already logs
  the actor at `answer_permission`; the ring is shown to the user, who does not
  need their own id.

## Required behavior

### Decisions taken in this spec (a reviewer may overturn them)

1. **A new variant, not a field on `RUN_RESUMED`.** `RUN_RESUMED` also follows
   a decision being answered and a fake's scripted resume; overloading it would
   make "resumed" mean "resumed, and maybe a permission verdict too". The new
   event is additive and an older client already renders an unknown variant as
   text (`run-console-model.ts`'s `default` arm), so nothing breaks.

   ```rust
   PermissionAnswered {
       /// Absent when the ask was refused before it was ever raised (a second
       /// ask, a malformed ask, a run that could not block) — no card was shown.
       ask_id: Option<String>,
       tool: String,
       verdict: AgentRunPermissionVerdict,   // ALLOW_ONCE | DENY
       decided_by: AgentRunVerdictSource,     // USER | POLICY
       /// What the child was told, for a denial. Absent for an allowance.
       reason: Option<String>,
   }
   ```

   `AgentRunVerdictSource` is a new run-lane enum (the lanes do not import each
   other). Field names are camelCase on the wire, spelled by hand as
   `CommandFinished.exitCode` is. `bounded()` clips `tool` to `MAX_TOOL` and
   `reason` to `MAX_REASON`.

2. **Recorded by the driver, at the moment it writes the answer to the child.**
   Not in `answer_permission`: the manager knows the user's verdict but not the
   words the child receives, and an answer the manager accepted can still fail
   to reach the child (the pipe breaks, the run fails). Recording where the
   answer is written records what actually happened. Concretely, one record
   per row of the driver's denial table:

   | Where | verdict | decided_by | reason |
   |---|---|---|---|
   | `Step::Answered(Some(AllowOnce))` | `ALLOW_ONCE` | `USER` | — |
   | `Step::Answered(Some(Deny))` | `DENY` | `USER` | `USER_DENIED_REASON` |
   | `Step::Answered(None)` (withdrawn) | `DENY` | `POLICY` | `DENY_BY_DEFAULT_REASON` |
   | `Step::Cancelled` with an ask outstanding | `DENY` | `POLICY` | `DENY_BY_DEFAULT_REASON` |
   | `raise`: a second ask | `DENY` | `POLICY` | `ONE_ASK_AT_A_TIME_REASON` |
   | `raise`: no tool named | `DENY` | `POLICY` | `MALFORMED_ASK_REASON` |
   | `raise`: the run could not block | `DENY` | `POLICY` | `DENY_BY_DEFAULT_REASON` |

   The record comes **after** the write succeeds. A write that fails already
   ends the run `FAILED` through `context.fail`, and the failure is the event
   that tells the story.

3. **The cancel path records before it terminates the child**, and the event is
   not lost to `record`'s terminal-state drop: at that point the run has
   `cancellation_requested` but is not yet `CANCELLED`, so `record` accepts it.
   The test below proves this rather than assuming it; if the supervisor's
   `CANCEL_JOIN_GRACE` aborts the driver first, say so in the report — T310-ANSWER
   already met a supervisor that aborted a driver before its cancel-time deny
   was written, and the answer then was to assert what the stub child received,
   not to lengthen the grace.

4. **The fake driver says the same thing.** `FakeAction::PermissionAnswered {
   granted }` records `PERMISSION_ANSWERED` with `decided_by: USER` and the
   matching verdict before its `RUN_RESUMED`, so a UI built against the fake
   draws the row a real run draws.

5. **The console draws one row:** `Allowed · Bash` or `Denied · Bash`, with the
   reason as the row's detail and "by policy" in the label when
   `decidedBy` is `POLICY`. Tone `permission`, like the ask it answers.

6. Fix the stale doc comment on `PermissionRequested` ("Reported, not
   answerable … a later task's here"): since T310-ANSWER it is answerable.

## Failure behavior

- A driver that dies between writing the answer and recording it loses the
  record, not the answer. Acceptable: the run's own ending is recorded.
- A reason longer than `MAX_REASON` is clipped, never dropped.
- An ask answered after its run ended records nothing (the ask is gone; the
  existing "answered after it had gone" rule is unchanged).
- The ring is bounded (`MAX_RUN_EVENTS`): a long run may evict an early
  verdict like any other event.

## Acceptance criteria

- A run that asks and is **denied by the user** shows, in order,
  `PERMISSION_REQUESTED`, `RUN_BLOCKED`, `PERMISSION_ANSWERED {DENY, USER,
  reason}`, `RUN_RESUMED` in its ring; allowed, the same with `ALLOW_ONCE` and
  no reason.
- Each `POLICY` row of the table above produces its record, including the
  cancel path.
- `T310`'s criterion holds as written: the console shows what was asked and
  why it was denied.
- An older renderer given the new event draws it as an unrecognised row and
  does not throw.
- `PROTOCOL_VERSION` bumped one minor, claimed in `docs/merge-queue.md`;
  generated types fresh.

## Tests required

- `claude_driver/tests.rs`: one test per table row against the stub child,
  asserting the ring *and* what the stub received (the verdict line), so a
  record cannot claim an answer the child did not get.
- `fake_driver/tests.rs`: a scripted allow and deny record the event.
- `wire.rs`: round-trip of the new variant (camelCase fields, absent `askId`
  and `reason` omitted) and `bounded()` clipping.
- `run-console-model.test.ts`: allowed, denied by user, denied by policy.
- Mutation check, stated in the report: delete the record in
  `Step::Answered` and the driver test fails; move the cancel-path record after
  `terminate()` and the cancel test fails (or report that it does not).
