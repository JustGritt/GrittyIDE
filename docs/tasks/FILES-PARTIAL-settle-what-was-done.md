# Task FILES-PARTIAL — A move or delete that stops partway settles what it did

- **Phase:** maintenance (an ADR-028 follow-up)
- **Status:** review
- **Depends on:** T042

## Objective

When `files.move` or `files.delete` stops before the end of its batch, because
an entry failed or the user cancelled, everything that already happened is
accounted for:

- moved documents follow their files;
- the completed part is undoable;
- the explorer re-lists;
- the answer says how far the batch got.

## Motivation

ADR-028 says a cancelled copy or delete "stops before the next entry, what was
already written stays, and the response names it", and that a move re-keys
open documents through `rehome`. On `6f074e6` neither holds once a batch stops
early.

- **A mid-batch failure loses the prefix.** `transfer_blocking` and
  `delete_blocking` (`files.rs:748-807`) use `?` inside their loops. When entry
  k fails, the count of the k-1 already done is discarded, and
  `finish_job(...)?` returns before `settle_transfer` runs. As a result:
  - the moved entries are not journaled, so ⌘Z cannot undo them;
  - `after_move` never rehomes their open documents, which keep the old path
    and read `DELETED_EXTERNALLY` at the next status check;
  - no `changed` directories reach the renderer, so the tree waits on the
    watcher, which ADR-028 says is not the contract.
- **A cancel past the budget settles nothing.** The operation body selects on
  `ctx.cancelled()`, but `OperationRegistry::run` (`registry.rs:222-252`)
  selects on the same token first and *aborts* the body. `finish`
  (`registry.rs:290`) then records `Cancelled` with no result, whatever the
  body returns. So `settle_transfer` never runs, and
  `FileOperationResult.cancelledAfter` cannot reach the wire at all.
- **`CancelOnDrop` is built inside `async move`** (`files.rs:428`, `:580`). An
  operation cancelled before its body is first polled drops the closure without
  cancelling the token, and the blocking job runs to the end unobserved.
- **The cross-device move fallback** (`mutate.rs:225-233`) reports a failed
  source removal against the *destination* path (`remove_native(&source, to)`),
  and has no test because the rename cannot be injected.

## Explicit non-goals

- **No rollback.** What was moved stays moved (ADR-028).
- **No change to the operation registry.** The operation model is frozen.
- **No new `CoreEvent`, no new wire type, no protocol version bump.** `details`
  is free-form JSON, and `cancelledAfter` stays on the wire.
- **No Trash-specific handling.** That is TRASH-FALLBACK.

## Required behavior

1. **The work settles itself.** The blocking job journals, rehomes and computes
   `changed` for exactly the entries it completed, whether it finished, failed
   at entry k, or was stopped by cancellation. Aborting the async body cannot
   skip it.
2. **A failure keeps its identity.** A failure during execution returns the
   original error's `code`, `retryable` and `details`, with
   `details.completed` and `details.requested` merged in. The message says how
   many entries were done first when that is more than zero. A refusal before
   anything ran (plan-time `Conflict`, `InvalidInput`, the dirty-document guard)
   carries no `completed` key.
3. **Cancellation reaches the job.** `CancelOnDrop` is owned by the operation
   closure, so a cancel at any point stops the job at the next entry.
4. **A late settle cannot damage the next workspace.** A settle for a workspace
   that is no longer open writes no journal entry and reads no labels.
5. **The renderer re-lists without knowing what changed.** On a files-kind
   `OperationFailed` or `OperationCancelled` for the open workspace, and on a
   move or delete error carrying `details.completed`, it re-lists every loaded
   directory, the answer ADR-025 already gives for `overflowed`.
6. **The cross-device fallback names the source** when removing it fails, and is
   tested through an injected rename.

## Failure behavior

| Situation | Behavior |
|---|---|
| Entry k of n fails | k-1 settled (journaled if a move or copy, rehomed, changed); error with `completed: k-1, requested: n` |
| Cancelled past the budget | Completed entries settled in the job; operation `CANCELLED`; renderer re-lists loaded nodes; open documents follow via `DocumentChanged { MOVED }` |
| Cancelled before the body first ran | The job is stopped at its first token check |
| Workspace closed or replaced before the settle | Rehome still attempted (the document layer ignores a gone workspace); no journal write |
| Body panics (`JoinError`) | Unchanged: `Internal`, no settle; renderer re-lists on `OperationFailed` |
| The in-flight entry finishes after `OperationCancelled` | Not re-listed by that event; the watcher covers it. Documented, not claimed |

## Acceptance criteria

- A three-entry move whose second source is missing leaves the first moved,
  rehomed and undoable, and answers `NotFound` with `completed: 1`.
- A cancelled over-budget move rehomes and journals what it completed.
- A refusal before any work keeps its error unchanged.
- `pnpm check` green, with regenerated protocol types committed.

## Completion report

### Summary

A move or delete that stops partway now accounts for what it did.

- **Settlement moved into the blocking job.** The job settles the entries it
  completed: journal, `rehome`, and the changed set. Neither an error at entry
  k nor a cancelled operation, whose body the registry aborts, can skip it.
- **The loops stop without discarding.** The two blocking loops return progress
  plus the error that stopped them, instead of `?`.
- **Errors say how far the batch got.** An execution error keeps its code and
  details and gains `completed`/`requested`. A refusal before any work is
  untouched.
- **The renderer re-lists.** It re-lists every loaded directory after a
  files-kind `OperationFailed`/`OperationCancelled`, or an error carrying
  `completed`.
- **Cross-device fallback.** It now names the source when removing it fails,
  and has tests.

The first draft of the cancel test did not isolate its path. It cancelled
before the operation's task was polled, so under the `CancelOnDrop` mutation
both cancel tests failed for the same reason. It now waits for `RUNNING`, and
the two tests cover the two cancellation paths separately.

### Architectural decisions

- **Settle in the job, not in the body.** The registry owns cancellation. It
  aborts a cancelled body and drops any result, and it is frozen, so the only
  code guaranteed to run after the last entry is the blocking closure itself.
  The locks it takes are std mutexes held per call, with the same order the
  async path used.
- **`completed` in `details` is the signal, not a new type.** An error for work
  that happened needs no new wire shape, and its presence tells the renderer the
  tree changed. No protocol bump.
- **`labels` became read-only.** It used to go through `with_journal`, which
  resets the journal on an id mismatch. A late settle for a closed workspace
  would have emptied the next workspace's undo history just by reading its
  labels.
- **`cancelledAfter` stays** and says it is not set. Removing a wire field is a
  breaking change, for no behavioural gain.

### Known limitations

- `OperationCancelled` is emitted when the body is aborted, before the entry in
  flight finishes. A re-list triggered by it can miss that last entry. Open
  documents are still right (`rehome` emits `DocumentChanged`); the tree relies
  on the watcher for that one entry. Closing it needs the registry to wait for
  the job, which it does not.
- A copy or cross-device move that fails *within* an entry leaves a partial
  destination tree that is not journaled, as ADR-028 accepts.
- The explorer's ⌘Z label is not refreshed after an error or a pending
  operation's completion. ⌘Z itself works; its label reads what the last ready
  response said.
- Nothing was clicked.
